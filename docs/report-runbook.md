# Report Runbook

How the weekly threat-intel report is produced, how to run one manually, and
why the staleness alarm stays manual. (Issue #77.) The reports in
[`reports/`](../reports/) are a frozen eval corpus, not this pipeline's output.

## What `reports/` is

Dated threat-intelligence reports generated by the
[`cyber-threat-intel` skill](../skills/cyber-threat-intel/SKILL.md), default
scope (`enterprise_soc` persona, `7d` lookback). Each report carries the
skill's honesty markers:

- **Coverage badge** in the header — `FULL` / `PARTIAL` / `MINIMAL`, an honest
  self-report of how many sources were actually consulted (R4). `MINIMAL` on a
  quiet week is correct, not a failure.
- **Methodology notice** — states plainly what retrieval was available (live
  MCP feeds, web search, or training data only) and what that means for the
  findings.
- **Appendix A: Source Coverage Ledger** — per-tier record of what was and
  wasn't consulted (R5).

Reports never contain fabricated indicators (R3): a report generated without
live feed access says so and contains no literal IOC values.

## How reports are generated

[`scheduled-report.yml`](../.github/workflows/scheduled-report.yml) runs the
skill against feed data a separate, credential-holding job has already fetched
(see below — the agent has no MCP feed server), and **publishes the report to
the run's summary page and its job log** — it is not committed. The job-log
copy is the one an agent session can read back: the summary has no REST API,
and direct artifact downloads (`gh run download`) hit a blob host sandboxed sessions cannot reach (the GitHub connector route worked on 2026-11-16; see below). It
is printed with workflow commands suspended, because the text derives from
untrusted feed content.

> **`reports/` is frozen at 11 (2026-09-03).** It is the eval corpus that
> `evals/run.py --corpus` checks on every PR, not an archive of runs, and CI
> pins the count. A run writes to gitignored `report-output/` and the summary
> step publishes it; nothing is added to `reports/`. A run is useful, a
> permanent history of runs is not — read it in the Actions run, or copy it out.

It runs **weekly on a cron (Mondays 05:23 UTC), restored 2026-09-20**, and can
still be triggered on demand from Actions → scheduled-report → *Run workflow*
with a chosen persona and time range.

> **The weekly cron was removed (#170), then restored.** Each run costs a full
> agent session — the first successful one took 50 turns — to report on three
> keyless feeds, which was not worth a standing weekly charge. That was true of
> run `33326622088` (2026-08-30), the run the removal was decided against; it
> stopped describing the pipeline well before the cron came back.
> [#169](https://github.com/kj299/threat-intel/issues/169) named the trigger
> for revisiting it — three or more additional sources configured — and that
> has been met on keyless sources alone: OpenPhish, EPSS, OSV and Feodo Tracker
> need no credential (they are consulted whenever their fetch succeeds), on top of the original three (ThreatFox — since moved to a keyed API — CISA KEV and NVD).
> `prefetch_feeds.py` also reaches every credentialed adapter with a
> configured key, which only adds to that count.
>
> Meeting the count is not the same as clearing the bar on its own — a routine
> run only earns its cost if it improves the tooling or the capability, not by
> re-proving a pipeline that is already proven (CLAUDE.md's Operator
> Principle, 2026-09-04). That was the operator's call to make, and it was
> made: the #169 trigger fired and the cron was restored on 2026-09-20. The
> matching alarm in `report-staleness.yml` was **not** restored alongside it —
> see the Staleness guard section below for why that pairing was deliberately
> broken. #169 also records why weekly rather than daily.

**Enabling it:** the workflow needs one credential, as a repository secret.
Either works, and they bill differently:

| Secret | Where it comes from | Billing |
| --- | --- | --- |
| `CLAUDEOUATH` *(or `CLAUDE_CODE_OAUTH_TOKEN` — either name is read)* | `claude setup-token` | Against a Pro / Max / Team / Enterprise subscription |
| `ANTHROPIC_API_KEY` | [Claude Console](https://platform.claude.com) | Per token, **and requires credits** |

**These are two different credentials, and only one of them exists on a web
page.** A Console API key (`sk-ant-api…`) is copied from
[platform.claude.com](https://platform.claude.com). An OAuth token
(`sk-ant-oat…`) is produced *only* by running `claude setup-token` in a
terminal — there is no page to copy it from. Pasting an API key into the OAuth
secret does not make it one.

The workflow checks the format of whatever is in the OAuth secret: an API key
(`sk-ant-api…`) pasted there is routed to the API-key input, and the run logs a
warning saying so. The reverse is not detected: an OAuth token placed in
`ANTHROPIC_API_KEY` is passed as an API key. Neither can be converted into the
other.

Set whichever suits you. The weekly cron is on (restored 2026-09-20), so this
is a standing cost: one agent session every Monday, plus any dispatches. A Console API key is a separate product from a
Claude subscription and is **not** funded by one: a brand-new key on an account
with no credits shows as `Active` and still fails every request.

**If you use an identity-linked API key** — one scoped to *All workspaces*
rather than a single workspace — the API additionally requires a workspace ID
and rejects the request without it:

> `400 anthropic-workspace-id is required when authenticating with an
> identity-linked API key`

Set an `ANTHROPIC_WORKSPACE_ID` repository secret to supply it. A workspace-scoped
key and an OAuth token both need nothing extra.

**The OAuth token wins when both are set**, and the generate step passes only
the chosen credential — the other is blanked. This is deliberate, and it is the
opposite of Claude Code's own
[credential precedence](https://code.claude.com/docs/en/iam#authentication-precedence),
which ranks `ANTHROPIC_API_KEY` higher. Passing both would let a leftover API
key silently override the token the repo is actually configured for, so nobody
has to delete a secret to make the configured one take effect.

With neither set, a manual dispatch is a green no-op: the report steps skip
with a notice, so the workflow will not fail on dispatch in an unconfigured
repo or fork. The `prefetch` job still runs, since it needs no model
credential. A **scheduled** run with neither set fails instead: the weekly
report stopping silently is a fault, and nothing else would say so.

### Feed credentials never go in the agent's job

The agent's job (`generate`) needs no feed API keys: it reads a data file the
`prefetch` job wrote. **Do not add `QFEEDS_API_KEY`, `VIRUSTOTAL_API_KEY`, or any
other feed credential** to `generate`; they belong in `prefetch` alone. CI blocks
it (*Agent credential isolation* in `validate.yml`), and the reason is worth
understanding before working around the check.

This workflow runs an LLM agent whose entire job is to ingest untrusted content
— threat feeds, vendor blogs, leak-site aggregators, arbitrary web pages —
and its output is published to the run summary and job log. That is a
prompt-injection surface by construction: the reports quote adversary-controlled
text. Any credential in that step's environment is reachable by the agent and
can leave in the published report, where masking catches only an exact value,
never a transformed one. The job is read-only (`contents: read`, no app token,
no persisted checkout credential), which limits what an injection can *change*,
not what it can *say*.

Narrowing `--allowedTools` does not mitigate it. Claude Code runs a built-in set
of read-only Bash commands *without consulting the allowlist*, and that set
includes `echo` and `cat` — the [permissions
docs](https://code.claude.com/docs/en/permissions) state it "is not
configurable". So `echo $VIRUSTOTAL_API_KEY` is available under any Bash allow
rule, and writing deny rules for every way a shell can read its own environment
is whack-a-mole that would only look like protection.

This is now implemented, and as a **separate job** rather than a separate step
(#169). The `prefetch` job holds every feed credential, runs a fixed script
([`mcp/scripts/prefetch_feeds.py`](../mcp/scripts/prefetch_feeds.py)), and
uploads the result as an artifact; the `generate` job runs `needs: prefetch`,
downloads that file, and holds no feed credential at all.

The job boundary is the point. Steps share a runner, so a "separate step" leaves
the credential on the same machine as the agent — in a prior process, possibly
in a file. Separate jobs get separate machines, so the agent's runner never
holds a feed credential in any form at any moment. The script also refuses to
write a payload containing any credential it holds, and the `prefetch` job is
narrowed to `contents: read` since it only fetches and uploads.

The agent no longer has the MCP feed server connected. Re-fetching from that job
would produce a second, strictly worse picture — no credentials there, so every
credentialed feed would come back `unverified` and contradict the file — and two
disagreeing accounts of the same feeds is what the honesty rules exist to
prevent. It also shrinks the tool surface an injection in the feed content could
reach.

`validate.yml`'s isolation check is scoped to the agent's **job** accordingly. It
derives which job that is from whichever one invokes `claude-code-action`, so a
second agent job is covered automatically, and it fails if no such job is found
rather than passing while guarding nothing. `mcp/src/threat_intel_mcp/vault/env.py` makes the same point about
environment variables generally, and a scheduled Actions job is a non-local
deployment by its own definition.

Runner egress matters here: GitHub-hosted runners have open outbound internet,
so the keyless feeds are reachable from Actions even where a restricted dev
sandbox blocks them. The `prefetch` job proves this per-run: it runs
`prefetch_feeds.py --require-records` and **fails loudly** — so `generate` never
starts — only when *every* source degraded, rather than quietly producing
another no-live-data report. A single dead feed does not abort the report; it is
recorded `unverified` in the ledger with the reason the prefetch saw. (Until
2026-10-26 `generate` opened by re-fetching ThreatFox and CISA KEV itself and
failed on either, so when ThreatFox's CSV export started answering `410 Gone`
the whole weekly report was lost.)

Historically the cadence ran from an operator's own scheduled Claude Code
session, which is exactly why it could die unnoticed: nothing in the repository
described or ran it.

### Manual generation

> **On Windows, follow [`report-runbook-windows.md`](report-runbook-windows.md)
> instead.** It is this section rendered in Windows PowerShell 5.1, and it
> covers the platform failures that stopped the first live run (#76) — the
> missing `py` launcher, the off-`PATH` console script, TLS 1.0 defaults,
> here-string and BOM traps, and native stderr being rendered as an error.

1. **Environment.** A Claude Code session on this repository. For a
   live-data report, configure the `threat-intel-mcp` server first (see
   [`mcp/README.md`](../mcp/README.md) — Quick start / Wire into Claude Code).
   The keyless sources (CISA KEV, OpenPhish, Feodo Tracker, EPSS and OSV;
   NVD also works unkeyed at a lower rate limit) are enough for a first live
   run. ThreatFox is no longer keyless: its authenticated JSON API needs
   `ABUSECH_AUTH_KEY`, and without it the feed is recorded `unverified`.

   > **Egress requirement:** the session's network policy must allow HTTPS to
   > the feed hosts (`www.cisa.gov`, `services.nvd.nist.gov`, `openphish.com`,
   > `feodotracker.abuse.ch`, `api.first.org`, `api.osv.dev`, `raw.githubusercontent.com` (OpenPhish's redirect target and CISA KEV's fallback mirror), plus
   > `threatfox-api.abuse.ch` and any other keyed feeds). Restrictive cloud
   > sandboxes may block these (proxy `CONNECT 403`) — verified blocked in the
   > default cloud environment on 2026-07-24. Run from an environment with
   > open egress, or accept a no-live-data report that says so.
   >
   > **This is per-environment and it changes — check, don't assume.** On
   > 2026-09-12 a Claude Code on the web session reached every keyless feed
   > through the agent proxy and completed a full 7d prefetch: ThreatFox 8,024
   > records, OpenPhish 300, CISA KEV 1,709, NVD 7,126, EPSS 499 scored, OSV
   > queried. The 2026-07-24 result above was real when recorded and is not
   > retracted; it is simply no longer a reason to skip the attempt. Probe
   > first — `curl -s -o /dev/null -w '%{http_code}'` against
   > `https://feodotracker.abuse.ch/downloads/ipblocklist.json` and
   > `https://www.cisa.gov/sites/default/files/feeds/known_exploited_vulnerabilities.json`
   > costs seconds and settles it. (ThreatFox's CSV export is retired — it
   > answers HTTP 410 — and its JSON API needs a key, so it is not a useful
   > unauthenticated probe.)

2. **Invoke** the skill (`/threat-intel:cyber-threat-intel` from a plugin load; see the note below), defaults or a chosen persona
   and time range.

   > **The slash command only exists if the repository is loaded as a plugin.**
   > Claude Code discovers skills from `~/.claude/skills/`, `.claude/skills/`,
   > and installed plugins — a top-level `skills/` directory at a repository
   > root is *not* a discovery location, so a plain clone exposes no
   > `/cyber-threat-intel`. This is why the first live run (#76) reported
   > `Unknown command`.
   >
   > `.claude-plugin/plugin.json` makes this repo a plugin whose skills live in
   > `skills/` — its existing layout. Load it for a session straight from the
   > clone:
   >
   > ```bash
   > claude --plugin-dir .        # run from the repository root
   > ```
   >
   > The command is then `/threat-intel:cyber-threat-intel` (plugin skills are
   > namespaced by plugin name; verified live 2026-09-02). The bare
   > `/cyber-threat-intel` only exists after a personal or project install.
   > The manifest bundles the MCP server too, so this single flag covers step 1
   > as well — subject to the usual per-server approval prompt.

   With MCP connected, the skill's Workflow step 2a calls
   `fetch_all_iocs` / `fetch_all_cves` and folds live results in; sources the
   tools report as degraded stay `unverified` in the ledger — never upgraded.
3. **Review:** badge consistent with the ledger; every IOC carries a real
   `source`; the methodology notice matches what was actually connected.
4. **Keep it outside `reports/`** -- e.g. `report-output/`, which is gitignored.
   Do not commit it: `reports/` is the frozen eval corpus, and `validate.yml`
   fails any PR that changes its count.

## Staleness guard

[`report-staleness.yml`](../.github/workflows/report-staleness.yml) checks
whether anything has touched `reports/` in the last **10 days** and opens (or
bumps) a `Report pipeline stale` issue if not.

It is **manual-only, and deliberately so** (#170): with nothing committing to
`reports/`, its condition is permanently true, so on a schedule it would refile the same issue forever —
noise that trains people to ignore the alarm. It and `scheduled-report.yml`
were designed as a pair, meant to restore together once #169's trigger fired
(see "How reports are generated" above) — but only `scheduled-report.yml`'s
cron came back on 2026-09-20. The pairing doesn't hold any more: `reports/` is
a frozen eval corpus (validate.yml pins it at 11) and the generator publishes
to its run summary rather than committing, so `reports/`'s git history will
never move again no matter how often the generator runs. This alarm watches
that history, so restoring its cron today would not detect a dead cadence —
it would refile the exact permanent alarm #141 already closed, once and then
forever, for a reason unrelated to whether reports are actually being
generated. It stays manual-only until a home for new, non-frozen-corpus
reports is chosen; the intended 54-minutes-after-generation offset (06:17 UTC
against the generator's 05:23 UTC) stays documented in `report-staleness.yml`'s
own comment for whoever makes that call.


## Fresh ThreatFox input for a separate daily report

> **Superseded as the preferred route (checked 2026-11-21).**
> `threatfox-prefetch.yml` has been scheduled on `main` since #251 and is the
> daily ThreatFox producer; see *Durable read-only daily handoff* below. The
> dispatch route in this section still validates in `consume_threatfox.py`, but
> it runs a full agent session and uploads a second `threat-intel-report`
> artifact, so use it only as a manual fallback.


The daily consumer does not receive `ABUSECH_AUTH_KEY`. Reuse the existing
credential-isolated `scheduled-report` prefetch job with a **24h** input, then
retrieve its scanned `feed-data` artifact. This workflow also queries other
feeds, performs enrichment and runs a model-generated report; it is not a cheap
ThreatFox-only endpoint. No new workflow, schedule, or permissions are installed
by the consumer helper.

With authorized GitHub CLI access, capture the current main SHA and dispatch:

```bash
gh api repos/kj299/threat-intel/branches/main --jq .commit.sha
gh workflow run scheduled-report.yml --repo kj299/threat-intel --ref main \
  -f persona=enterprise_soc -f time_range=24h
gh run list --repo kj299/threat-intel --workflow scheduled-report.yml \
  --event workflow_dispatch --limit 10 \
  --json databaseId,headSha,createdAt,status,url
```

Resolve the run using the captured SHA and dispatch start time; do not guess if
concurrent dispatches make it ambiguous. An existing run may be reused only
when its acquisition is within the daily consumer's freshness budget and it
passes the same checks. Save API metadata for the exact run and artifact:

```bash
gh api repos/kj299/threat-intel/actions/runs/RUN_ID > run.json
gh api repos/kj299/threat-intel/actions/runs/RUN_ID/jobs > jobs.json
gh api repos/kj299/threat-intel/actions/runs/RUN_ID/artifacts
```

Wait for `Fetch feeds (holds credentials; no agent)` to succeed and for its
non-expired `feed-data` artifact. Save that artifact's metadata object as
`artifact.json`. It is retained for one day. The separate generate job may
still be running or fail; its outcome does not invalidate a successful prefetch.
Limit the wait to the report's remaining delivery budget; if unavailable,
continue the daily report with ThreatFox unverified. Do not repeatedly dispatch
or consume a previous weekly report as fresh input.

Download only the exact validated artifact. The GitHub connector's
`download_workflow_artifact` can retrieve it when direct `gh run download` is
blocked at the artifact host. This route was verified for report artifacts on
2026-11-16; availability must be checked in each runtime. Inspect the ZIP and
extract only the expected regular `feed-data.json` member, with an explicit
uncompressed size limit;
do not execute artifact content or extract arbitrary paths.

```bash
python scripts/consume_threatfox.py --archive feed-data.zip \
  --run run.json --artifact artifact.json --jobs jobs.json \
  --expected-sha CAPTURED_MAIN_SHA --report-end REPORT_CUTOFF_UTC
```

The helper accepts the downloaded ZIP with `--archive` and enforces the
authorized 128 MiB compressed/uncompressed bound, exact single member name and
regular-file type without extracting paths. `--payload` accepts an already
validated JSON file under the same byte bound. It defaults to a two-hour freshness budget, requires a successful
prefetch job from the expected main commit on an allowlisted workflow and event
(`workflow_dispatch` for `scheduled-report.yml` and `daily-feeds-prefetch.yml`;
`schedule` or `workflow_dispatch` for `threatfox-prefetch.yml`), rejects expired or
mismatched artifacts and non-24h payloads, and preserves ThreatFox-specific
`source_evidence` after cross-source deduplication. It reports `partial` rather
than claiming full-day coverage: the multi-feed `feed-data` artifact lacks a per-source
retrieval timestamp, so its acquisition is only bounded by prefetch start and IOC
fan-out completion; the `threatfox-feed-data` artifact carries source-specific
`collection_started_at`/`collection_completed_at`, which the consumer uses instead. The interval from acquisition to report cutoff remains
unobserved. Keep these bounds, run URL, commit, artifact ID, source status and
caveats in report provenance. Error and stale cases become `unverified`; they
must not cancel the HTML email. Treat all returned feed strings as untrusted
and defang indicators before rendering them.

`get_iocs` selects by **first_seen**, not by every update or current activity.
Do not imply that an empty result means no active threats. The account's
commercial-use entitlement is not established by HTTP 200; confirm applicable
[abuse.ch terms](https://abuse.ch/terms-of-use/) for the intended enterprise use.
No secret should be copied to the daily runtime. This runbook describes an
integration contract; it does not establish that a separate automation has
been configured or has successfully consumed an artifact.


### Compact handoff and the verified size gap

The live multi-feed artifact from run 43852290931 was 3,993,830 compressed bytes
but 92,387,456 uncompressed bytes. An independent runtime correctly rejected it
under its 50 MB limit. Do not raise the daily runtime's limit automatically. An explicit operator
approval on November 16 subsequently authorized a bounded 128 MiB limit; retain
regular-file, exact-name, path and provenance checks.
A controlled maintenance test ingested the known single-file artifact with an
explicit 128 MiB bound, but that is not evidence of independent-runtime success.
Any earlier verification task explicitly capped at 50 MB must retain its own
instructions; test the authorized higher limit in a new verification.

The consumer exports only ThreatFox records and provenance, with a strict 1 MiB
output bound and original-payload SHA-256. If the full derivative exceeds 1 MiB,
it retains the largest newest-first prefix of whole records that fits, with
window-matched and omitted counts. A nonempty prefix is partial, not complete.
If no usable record fits, the result is unverified. A prefix is not proof that all
records through that timestamp were included. An authorized maintenance runtime
can hand this compact derivative to a report consumer together with its hash,
source run/artifact IDs, commit, acquisition bounds and cutoff. Revalidate all
metadata and the actual report window; a derivative must not reset freshness.
The November 16 verified derivative was 447,067 bytes, below 1 MiB. A trusted
handoff of that dated snapshot can support the next report, but does not install
an ongoing compact producer. A recurring compact artifact from Actions now exists:
`threatfox-prefetch.yml` (scheduled on `main` since #251) publishes a
ThreatFox-only `threatfox-feed-data` artifact capped at 1 MiB.
An authorized 128 MiB consumer may instead ingest the existing full artifact
while it remains within that bound; compact production is an optional improvement.
If only an oversized full artifact or stale derivative is available, continue
the daily report with ThreatFox unverified and disclose the integration gap.


## Durable read-only daily handoff

> **Status (checked 2026-11-20):** the schedule below was merged in #251 and is
> active on `main`. Scheduled runs succeeded on 2026-11-16 through 2026-11-19.
> A green run still does not prove ThreatFox answered:
> read the packet's source status.

Independent verification established that the daily inherited runtime can
retrieve and parse artifact 14220190745 under the explicitly authorized 128 MiB
limit, but its `gh` has no authenticated session and it has no dispatch connector.
Do not claim that a prompt instructing it to dispatch creates that capability.

The [`threatfox-prefetch.yml`](../.github/workflows/threatfox-prefetch.yml)
schedule runs at **06:40 America/New_York**, before the separate 07:00 report.
GitHub now supports an IANA `timezone` on `schedule`, including DST; see
[official schedule documentation](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule).
Scheduled runs may be delayed or dropped, and only run from the default branch.
(When this was written the cron existed only on a PR branch; it is on `main` now.)

This producer has `contents: read`, no email or model step, a five-minute job
limit, and only `ABUSECH_AUTH_KEY` in the fixed fetch step. It calls `get_iocs` for 24h with at most one retry, on `httpx.RemoteProtocolError` only, after a 0.25–0.5 s backoff, with both attempts inside the same 90-second deadline (`attempt_count` in the packet is metadata, not a coverage upgrade; authentication, HTTP-status and schema failures are not retried). It schema-validates
and deduplicates network records, records source acquisition start/end, scans
literal and JSON-escaped credential values, and caps `feed-data.json` at 1 MiB.
Missing-key/upstream failures publish an honest `unverified` packet. On overflow,
the artifact keeps the largest newest-first prefix of whole normalized records
that fits and reports exported, original and omitted counts; a nonempty prefix
is partial, and no usable record fitting yields unverified. The credential
scan checks the full candidate before compaction and the final output, so even
a would-be omitted credential prevents publication entirely. The artifact name is **threatfox-feed-data**, retained one
day. Upstream success is not inferred from a green job: read packet source status.

The daily runtime only needs read access:

1. Read recent runs of **threatfox-prefetch.yml** via GitHub (schedule or manual
   event), pin the trusted main commit and exact run, and verify the successful
   **Fetch ThreatFox (holds credential; no agent)** job.
2. Retrieve that run's unexpired **threatfox-feed-data** artifact and verify its
   run/commit association. Download through the connector, not an unauthenticated
   CLI. Require exactly regular `feed-data.json` and enforce byte limits.
3. Run the consumer's `--archive` path with API-sourced run/jobs/artifact metadata.
   It accepts three allowlisted routes: the scheduled `threatfox-prefetch.yml`,
   the manually dispatched `scheduled-report.yml` prefetch, and the manually
   dispatched `daily-feeds-prefetch.yml`. It uses source-specific acquisition bounds when
   present and preserves partial status for the gap before report cutoff.
4. Reject stale/malformed/missing data and keep the daily email on schedule using
   other verified sources. Never try to repair missing dispatch privileges by
   copying a token or a feed key into the daily runtime.

The schedule was merged in #251 and scheduled runs have succeeded daily since
2026-11-16, so the daily task's preferred lookup can point at this workflow. A
green run is still not proof that ThreatFox answered: inspect the packet's source
status. Confirm applicable commercial-use entitlement; HTTP success is not
evidence of that entitlement.

## Independent pre-report fallback (helper merged; no scheduler deployed)

On November 16, the first `schedule` run (43957744610) was created at
21:12:47 UTC for the unchanged 06:40 America/New_York workflow. The job started
at 21:12:50 and succeeded at 21:13:12. This is 9h32m47s after the intended
11:40 UTC time, not nine hours spent queued after run creation. The API exposes
no original enqueue timestamp or scheduler cause. Workflow history contains only
its original addition; it remains active. GitHub documents possible schedule
latency/drops and valid timezone syntax; neither establishes the cause here.
[GitHub's incident](https://www.githubstatus.com/incidents/2zfqmghmg3s3)
opened at 11:59 UTC initially for Pull Requests, explicitly listed Actions

as of 12:06 without admitting 12:03 publications. Omitting the field preserves
